# Спецификация: ForwardTrace v2 — разговорный дневник прогресса

## Как читать

Бриф (`2026-10-26-brief.md`) уже написан как техническое задание: модель данных, API, логика, этапы, конфигурация. **Его разделы действуют дословно и являются частью этой спецификации**; каждый тикет цитирует нужные места. Здесь — только то, чего в брифе нет: решения брифинга, проработка (что бывает, когда что-то идёт не так), решения по реализации и границы модулей (`interfaces.md`). Где этот файл и бриф расходятся, верен этот файл — расхождения перечислены в §1.

Факты о текущем коде — в `notes.md`; где он расходится с `DOCUMENTATION.md`, верен код.

## Задача

«Я долго учу английский (пишу игру, бегаю) и не вижу, что расту. Обычный ИИ-чат каждый раз забывает, что я рассказывал, и хвалит ни за что. Мне нужен собеседник, который помнит мои же слова с датами и показывает: вот здесь вы застревали, а теперь справляетесь».

## Решение

Каждый день — один разговор голосом или текстом. ИИ отвечает сразу, потоком, и ссылается на прошлое только дословными цитатами из ваших же сообщений с датами — цитаты подставляет код. Трудности становятся нитями; когда вы говорите, что справились, появляется карточка «было → стало». Раз в день в выбранный час ИИ пишет первым (push или Telegram). Первый разговор — это и есть онбординг: навык, мотивация, финиш, точка старта, первое «тогда → сейчас». Экраны: Сегодня (лента недели + разговор), История (дни и поиск), Прогресс (цель, финиш, путь словами человека, карточки, нити, месячная сводка), Профиль. Бесплатно — первые 7 дней без ограничений, потом 3 разговора в неделю; «Plus» — фейковая дверь, дающая месяц безлимита.

## 2. Решения по реализации

- **Postgres для проверки миграций** — локально установлен Docker; если демон не запущен, исполнитель этапа 1 запускает Docker Desktop и поднимает `postgres:16` из `docker-compose.yml`.
- **Ветка `v2` от `main`** — создана. Коммиты небольшие, по тикету. (R017, R204 брифа «Правила»)
- **Тесты:** `cd progress-backend && ../venv/Scripts/python.exe -m pytest -o addopts= -q`. Фронтенд: `npx tsc --noEmit && npm run build`. Новые тесты — в новых файлах `tests/test_v2_*.py`, тот же стиль (`httpx.AsyncClient` + `ASGITransport`, `pytest.mark.asyncio`), общие фикстуры и подмены провайдеров — в `conftest.py`. Каждый модуль, импортирующий `complete_json`/`stream_chat`/`embed`/`transcribe` по имени, подменяется в автофикстуре — без ключей реальные вызовы падают.
- **Миграция `0014_v2_core`** (`down_revision = "0013_account_deletion"`), стиль файлов как в 0013, типы `JSONB`/`UUID` как в `0001_baseline`. Удаление таблиц v1 — `0015_drop_v1`. Тесты используют `create_all`, а миграции написаны под Postgres и на SQLite не идут. Поэтому проверка «на чистой базе и на базе с данными v1» (R189) — тест с маркером, который выполняется при заданном `TEST_POSTGRES_URL` (применяет 0001→head на пустой базе; затем на базе, доведённой до 0013 и заполненной данными v1, применяет 0014 и запускает импорт) и пропускается с причиной без него. Исполнитель этапа 1 запускает его на локальном Postgres, если тот доступен (docker), и пишет результат в отчёт этапа; недоступен — строка в отчёте сборки. Тест импорта на SQLite (через `create_all` с моделями v1 и v2) работает всегда.
- **LLM:** `complete_json` получает необязательные `model=` и `reasoning_effort=` (обратно совместимо). `stream_chat()` — тот же `httpx`, Chat Completions с `stream: true` и `stream_options.include_usage`, разбор `data:`-строк; стоимость пишется через `costs.record_llm` по итоговому `usage`. Эмбеддинги — `embed(texts)` через `POST /embeddings`, пустой `EMBEDDING_MODEL` → поиск по дате. Никакого SDK.
- **SSE** — `StreamingResponse(media_type="text/event-stream")`, заголовки `Cache-Control: no-cache`, `X-Accel-Buffering: no`. Генератор потока открывает **свою** сессию БД (`SessionLocal`): сессия из `Depends(get_db)` закрывается до отправки тела. Проверки «до начала потока» (лимит, почта, формат и размер аудио, пустой файл, ответ уже генерируется) выполняются в обработчике до создания `StreamingResponse` и отдаются обычным JSON с `{"detail": {"code", "message"}}`.
- **Ответ не зависит от соединения:** генерация ответа идёт в отдельной `asyncio`-задаче, которая пишет события в очередь; поток читает очередь. Если клиент отключился, задача доводит ответ до конца и сохраняет сообщение — после перезагрузки страницы ответ на месте.
- **Telegram** — `httpx` к Bot API, вебхук проверяет заголовок `X-Telegram-Bot-Api-Secret-Token` против `TELEGRAM_WEBHOOK_SECRET`; без `TELEGRAM_BOT_TOKEN` эндпоинты отвечают 503 `telegram_disabled`, канал telegram в профиле скрыт.
- **Push:** тег уведомления в `sw.js` — из payload (`tag`), по умолчанию `ft-<дата>`; тело без плейсхолдеров, цитаты в «ёлочках».
- **Аналитика:** один помощник `services/events.py::log_event` пишет `events` с `day_number` (дней с регистрации по локальной дате), `language` (`users.locale`), `channel` (`users.outreach_channel`). Все события этапа 9 идут через него; события с клиента (`quote_opened`, `feed_opened`, `week_strip_day_opened`, `progress_opened`, `pair_shown`, `paywall_viewed`) — через существующий `POST /api/events`, сервер дополняет их теми же полями.
- **Ошибки новых эндпоинтов** — `{"detail": {"code", "message"}}` через один помощник; фронтенд переводит по `code`, неизвестный код → общий текст «Что-то пошло не так». Старые эндпоинты аутентификации отдают строки как раньше; фронтенд для них показывает текст сервера только для 409/429/410 известных случаев, иначе общий текст.
- **Страна по умолчанию** (`users.country`) — из таймзоны по встроенной таблице частых зон (KZ, RU, UA, BY, UZ, KG, GE, AM, AZ, DE, GB, US, CA, FR, ES, IT, PL, TR, IL, AE, IN, CN, JP, AU…); неизвестная зона → `null` → контакты `default`.
- **Неделя лимита** — с понедельника по воскресенье в часовом поясе человека. Пробный период — пока локальная дата < дата регистрации (локальная) + `FREE_TRIAL_DAYS`.
- **Дизайн фронтенда** — функциональный: `app/tokens.css` — все цвета, отступы, радиусы, шрифты; тёмная (по умолчанию) и светлая темы через `data-theme`, как в v1; Tailwind `@theme inline` ссылается на токены. Шрифты v1 сохраняются (кириллица уже подключена). Без библиотек компонентов. Мобильная вёрстка 375 px, десктоп — колонка до ~640 px по центру.
- **Язык интерфейса** — `users.locale` после входа, до входа — `detectLocale()`; переключатель в профиле меняет `users.locale` (PATCH `/api/auth/me` должен принимать `locale` — уже принимает). `<html lang>` обновляется.
- **Лендинг** — статический `public/landing/`; на этапе 10 тексты ru/en в `shared/copy.js` переписываются под разговорный формат на «вы» — это **черновик**, в отчёте сборки — пункт «согласовать текст лендинга».
- **Админка** — Jinja-страницы переписываются на v2-данные на этапе 9 (метрики R200), старые страницы `entries`/`feedback` уходят вместе с таблицами.

## 4. Этапы → тикеты

Работа идёт этапами брифа 0–10, по порядку; следующий этап не начинается, пока не выполнены критерии готовности предыдущего («Готово, когда …» брифа) и не проходят тесты. Критерий, который нельзя проверить в этой среде (Postgres, браузер), не останавливает сборку: он записывается в отчёт этапа и в отчёт сборки как непроверенный, с причиной. Внутри этапа тикеты могут идти параллельно, если их файлы не пересекаются. Конкретная нарезка — в `tickets/`.

## 5. Проверка пути в браузере (R194)

Критерий этапа 5 — путь «регистрация → первый разговор голосом и текстом с выбором финиша кнопкой → сравнение → выбор часа → уведомления → зелёный день → свайп недель → тап по зелёному дню → проигрывание цитаты» в браузере 375 px. Он проверяется **на этапе 5**, до перехода к этапу 6:
1. всегда — тест бэкенда, проходящий тот же путь через API (регистрация, все шаги первого разговора текстом и голосом с замоканным STT, календарь, день в истории, аудио сообщения цитаты), и сборка/типы фронтенда;
2. если в сессии есть инструмент браузера — живой проход на 375 px с бэкендом на локальной базе; голос, которого автоматика не может надиктовать, заменяется загрузкой готового аудиофайла через тот же эндпоинт;
3. чего нельзя проверить в среде — в отчёт этапа и сборки с чек-листом «пройти руками» в `docs/v2/stages.md`.

## 6. Тексты сервера на «вы» (ru) — переводы шаблонов брифа

Английские версии — того же смысла. Все строки — в одном модуле текстов сервера (`services/texts.py`), фронтенд — в `lib/i18n.ts`.

- Создание первого разговора: «Здравствуйте! Я помогу вам замечать, как вы растёте, — вашими же словами. Что вы сейчас развиваете?» Быстрые ответы: «Программирование», «Геймдев», «Иностранный язык», «Спорт», «Музыка».

# Часть 2 — v2.1: живой собеседник вместо анкеты

## Как читать (v2.1)

Второй бриф — `2026-10-27-brief.md` — изменения поверх готового кода; его разделы действуют дословно и являются частью спецификации, а при расхождении с первым брифом и с Частью 1 верен он. Здесь — решения брифинга, проработка и решения по реализации. Где эта часть и второй бриф расходятся, верна эта часть: расхождения перечислены в §2.1. Код как он есть — `notes.md` (снимок 2026-10-27).

## Задача (v2.1)

«Пишу ИИ, что собрал MVP, а он мне: „это пригодится в английском, какой шаг выберешь завтра — утром или вечером?“ Каждый ответ — оценка, связь с целью, следующий шаг и вопрос с вариантами. Он не слышит, о чём я говорю, и ведёт меня по сценарию, как трекер».

## Решение (v2.1)

ИИ в разговоре звучит как живой собеседник: говорит на «ты», коротко, идёт за мыслью человека, не тянет каждое событие к цели и не заканчивает каждую реплику вопросом. Он видит недавний разговор дословно, а не выжимки, и помнит жизнь человека шире навыка: события, решения, продолжающиеся темы. Человек видит в профиле, что о нём запомнено, и может удалить лишнее. ИИ пишет первым как приглашение поговорить, а не как проверку. Двойная отправка больше не дублирует сообщения, а цитаты читаются внутри фразы. Чтобы сравнить старый и новый тон, есть прогон эталонных диалогов через настоящую модель с отчётом бок о бок. Сборка останавливается на этом отчёте, пока владелец его не оценит.

## 2.2 Решения по реализации

**Идемпотентная отправка (R261, R262, G03).**
- Клиент генерирует `client_msg_id` (`crypto.randomUUID()`, а без защищённого контекста — запасной генератор UUID v4) на каждое новое сообщение: текст, голос, быстрый ответ. `pending` хранит тело **вместе с id**, поэтому «Повторить» после обрыва сети отправляет тот же id. Кнопка отправки, микрофон и быстрые ответы блокируются синхронно в обработчике нажатия, до первого `await`, и разблокируются после конца потока или ошибки.
- `POST /api/conversations/today/messages` принимает `client_msg_id` в JSON или полем multipart. Ключ необязательный: Telegram и старые клиенты шлют без него. Формат — строка до 64 символов из `[A-Za-z0-9-]`, иначе 422 `bad_client_msg_id` (новый код, сообщение ru/en).
- `messages.client_msg_id String(64) NULL` и уникальный индекс `uq_messages_user_client_msg (user_id, client_msg_id)`, миграция `0017_client_msg_id`. NULL не конфликтует.
- Повтор проверяется **до** проверок занятости, лимита и сохранения аудио: повтор не тратит лимит, не получает 409 и не пишет файл. Сначала проверяется in-process словарь `_inflight[(user_id, client_msg_id)] -> message_id` (заполняется в `prepare_message`, чистится в `finally` задачи ответа), затем БД.
- Ответ на повтор — тот же SSE-поток без вызова модели:
  - `user_message` (сохранённое сообщение);
  - если ответ ИИ на него уже сохранён — его сегменты событиями `delta`/`quote` и `done` с его `message_id`;
  - если ответ ещё пишется или не сохранён — `done {message_id: null, duplicate: true, quick_replies: [], used_fact_ids: [], intent: "normal"}`. Фронтенд и так перечитывает день после потока.
- «Ответ на сообщение» — первое сообщение ассистента в том же разговоре, созданное после него.
- Страховка от гонки: `IntegrityError` по уникальному индексу при вставке в `_reply` обрабатывается как повтор.
- Событие `message_duplicate {client_msg_id, state: "replayed"|"in_flight"}`.

**Цитата внутри строки (R263).** `QuoteChip` становится inline-элементом (`<span>` без `block`, `my-2`, переносов): «цитата» стилем `.said`, сразу за ней мелким приглушённым шрифтом короткая дата («12 окт»), в той же строке. По нажатию на цитату открывается всплывающее меню: полная дата, «Открыть день» (если не сегодня), проигрывание фрагмента (если есть аудио), «Это неточно». Пометка `recalled` переносится в меню. Текстовые сегменты вокруг остаются `inline` с `whitespace-pre-wrap`. Прежние функции чипа (событие `quote_opened`, `flagFact`, `PlayAudio`) сохраняются. Приёмка: сравнение «Смотри: в начале — «…». Сейчас — «…». Пройдено больше, чем кажется.» на ширине 375 px — один абзац без разрывов между цитатами и точками.

**Промпт разговора (R214–R222).** `prompts.py` хранит `CHAT_SYSTEM_RU` (текст брифа с правками §2.4) и `CHAT_SYSTEM_EN` (тот же текст по-английски, обычное you). Для других локалей берётся английский текст с `_write_in(locale)`. `_address_formally` к промпту разговора больше не добавляется: тон задан самим текстом.
- Блоки «мягче» (`soft`, уровень безопасности 1) и plateau (`mode="plateau"`, `plateau_note`) сохраняют смысл и становятся ru/en-парами того же вида. Они дописываются после основного текста.
- META-инструкция — дословно из брифа.
- `services/prompt_examples.py`: `EXAMPLES: list[Example]`, где `Example(kind, user: dict[lang, str], bad: dict[lang, str], good: dict[lang, str], todo: bool)`. Пять заполненных по брифу (с правками §2.4) и четыре `todo=True` с пометкой `# TODO(owner)` и пустыми текстами.
- `render_examples(lang, limit) -> str` берёт заполненные примеры по порядку, не больше `PROMPT_EXAMPLES_MAX` (новая настройка, 8). Пустые TODO не попадают в промпт.
- Блок озаглавлен как примеры тона, с оговоркой, что `f_12`, `f_87` в них — условные id, не факты.
- `fact_id` вида `f_12` не проходит `_PLACEHOLDER`, а значит молча выбрасывается рендерером.

**Реестр версий промпта (R269, §2.1 #9).** `prompts.CHAT_PROMPTS: dict[str, Callable[[ContextData, PromptOptions], list[dict]]]` с версиями `"v2.1"` (текущая, по умолчанию) и `"v2.0"` (прежний `CHAT_SYSTEM` дословно, с прежним видом истории ролями и `max_words=120` литералом внутри legacy-функции — она только для эталонов). Эталонный скрипт принимает имя версии или путь к `.txt` с шаблоном на плейсхолдерах v2.1 (`{goal}`, `{anchor_quote}`, `{finish_line}`, `{threads}`, `{facts}`, `{day_summaries}`, `{recent_messages}`, `{examples}`) — так владелец сравнивает свою правку промпта без кода.

**Сборка контекста по трём уровням (R223–R226, R241).** `build_context` делится на загрузку (`load_context_data(db, user, conversation, text, mode) -> ContextData`) и чистую сборку (`compose_messages(data, *, version="v2.1", soft, plateau_block) -> list[dict]`), которую вызывает и эталонный скрипт.
- `ContextData`: `locale`, `goal_title`, `anchor_quote`, `finish_line`, `threads: list[ThreadLine(id, title, kind, since)]`, `facts: list[FactLine(id, local_date, type, quote)]`, `day_summaries: list[(date, text)]`, `recent: list[RecentLine(local_date, role, text)]`, `current: str|None`, `known`, `recalled`.
- Уровень 1:
  - сообщения всех разговоров человека от новых к старым;
  - текст — как в `_plain` (цитаты как «…»);
  - оценка токенов — `ceil(len(text) / CONTEXT_CHARS_PER_TOKEN)` (новая настройка, 3; токенизатор не добавляется — новых зависимостей нет);
  - правило §2.1 #8;
  - строки в хронологическом порядке, вид `[2026-10-26] Ты:` / `[2026-10-26] ForwardTrace:` (ru) или `You:` / `ForwardTrace:` (en);
  - текущее сообщение в уровень 1 не входит.
- Уровень 2: открытые нити обоих видов, до `CONTEXT_THREADS`, по `coalesce(last_mentioned_on, opened_on) desc`, в виде `[id] (topic|struggle) title — с <дата>`.
- Уровень 3:
  - цель только активная (`_active_goal`);
  - до `CONTEXT_FACTS` фактов из `relevant_facts`, отсортированных по дате, в виде `[id] YYYY-MM-DD type: «quote»`. Заголовок блока говорит, что это утверждения на свою дату и более новое важнее;
  - выжимки дней (до `CONTEXT_DAYS`), только тех, чьих сообщений нет в уровне 1.
- Пустые блоки пишутся словом «нет» / «none», чтобы шаблон не ломался.
- `known` — переданные факты и факты, уже процитированные в сообщениях уровня 1.

**Модель (R227, R228).** Значение `CHAT_REASONING_EFFORT` по умолчанию становится `medium` (`config.py`, `.env.example`). `stream_chat` уже берёт `CHAT_MODEL` или `OPENAI_MODEL` и эту настройку. Служебные вызовы не меняются (`complete_json` → `OPENAI_MODEL` + `OPENAI_REASONING_EFFORT=low`; безопасность — `SAFETY_MODEL`).

**Быстрые ответы (R229, R230).** Код META не меняется: при ошибке разбора — `[]`, максимум — `MAX_QUICK_REPLIES`. Фейк `CHAT_REPLY` в `conftest.py` по умолчанию отдаёт `"quick_replies": []`. Первый разговор не трогается.

**Проверки ответа (R231–R233).**
- Удаляются `check_reply_rules`, `BANNED`, событие `reply_rule_violation` и их тесты.
- Событие `ai_reply` получает поля `words` (слова прозы без цитат), `questions` (число `?` в прозе), `mentions_goal`, `with_quote` (уже есть), `with_quick_replies`.
- `mentions_goal(text, goal_title, skill) -> bool` — одна функция в `conversation.py`, её же использует эталонный скрипт. Истина, если нормализованная (`verify.normalize`) проза содержит нормализованное название цели или навыка либо любое их слово от 4 букв.
- Ответ не обрезается и не перегенерируется.
- Жёсткие проверки остаются: META, принадлежность `fact_id` (`known`), безопасность, лимит контекста (§2.1 #8), ошибки модели.

**Память (R235–R249).**
- Миграция `0018_memory_kinds`:
  - `threads.kind String(16) NOT NULL server_default 'struggle'`;
  - `outreach.topic`: `thread → follow_up`, `yesterday → day`, `general → day` (у `general` в новом наборе нет пары);
  - downgrade обратный: `follow_up → thread`, `day → yesterday`, удаление колонки.
  - `facts.type` — строка без ограничения, данные не меняются.
- `FACT_TYPES` += `event`, `decision`.
- `MEMORY_SCHEMA` дополняется: `threads.open[].kind` (`struggle|topic`), `follow_up: {message_id, quote} | null`.
- Промпт памяти дополняется: нить `topic` закрывается (`close`), когда человек говорит, что вопрос решён или больше не актуален; нить `struggle` — когда говорит, что справился.
- Правила:
  - `struggle` открывается только на факте `struggle`, `topic` — на любом проверенном факте; не прошедшее — отбрасывается и считается;
  - `mention` — для обоих видов;
  - `close` для `struggle` — как раньше (`achievement`/`learned`), для `topic` — на любом проверенном факте.
- Модели передаётся список нитей с видом.
- Пары:
  - по закрытию — только из нитей `struggle`;
  - по сходству — только если факт-«тогда» не привязан к нити `topic`.
- `follow_up`:
  - сообщение должно быть из этого разговора, а цитата пройти `verify.quote_supported`;
  - пишется в `conversation.state["follow_up"] = {message_id, quote, local_date, used_at: null}` (словарь переприсваивается целиком, чтобы SQLAlchemy заметил изменение);
  - `null` от модели не стирает уже сохранённый, непроверенный отбрасывается и считается в `memory_dropped_facts` (`follow_up_dropped: 1`).
- Промпт памяти дополняется определениями `event`/`decision`/`topic`/`follow_up` и правилом «факт — то, что человек сказал, без интерпретаций».

**Память под контролем (R245–R248).**
- `GET /api/memory`: `ThreadOut` получает `kind`, нити `deleted` не отдаются, `GoalOut` уже несёт `why_text` и `finish_line`.
- `DELETE /api/facts/{fact_id}` → 204. Порядок действий:
  - удаляются пары, где факт — «тогда» или «сейчас» (явно, не надеясь на каскад SQLite);
  - обнуляются `threads.opened_fact_id/closed_fact_id`, указывающие на факт;
  - удаляется факт;
  - пишется событие `fact_deleted {fact_id, type}`.
  
  Чужой или несуществующий факт — 404 `not_found`. Сохранённые ответы, где эта цитата уже была показана, не переписываются: это собственная история человека. Из памяти, прогресса и контекста факт уходит.
- `PATCH /api/threads/{id}` — проверяется тестом для `topic`.
- Профиль, раздел **«Что я помню»** (en «What I remember»), интерфейс на «вы»:
  - цель, мотивация и финиш со ссылкой «Изменить», которая прокручивает к существующему разделу цели;
  - «Темы»: открытые нити обоих видов с кнопками «Закрыть» и «Удалить», закрытые — свёрнутым списком с «Удалить»;
  - «Факты»: последние 50, дата, тип словом, «цитата», «Удалить». Удаление после подтверждения, строка исчезает сразу, при ошибке возвращается с текстом ошибки;
  - пустые состояния: «Пока ничего — запоминаю по ходу разговоров».

**Сообщения ИИ первым (R250–R256).**
- `pick_topic`: `follow_up`, затем `anchor`, затем `day` (§2.1 #6).
  - `follow_up` берётся из `state.follow_up` последнего разговора с `counts_for_limit`, если `local_date ≥ today − OUTREACH_FOLLOW_UP_DAYS` (новая настройка, 3; заменяет `OUTREACH_THREAD_RECENT_DAYS`) и `used_at` пуст. При отправке `used_at` проставляется: один follow_up — одно сообщение, иначе неотвеченный превратится в ежедневную проверку.
  - `day` получает лёгкий контекст: выжимку вчерашнего дня, если есть.
- `OUTREACH_SCHEMA` → `{"text"}`, у сообщения ИИ первым `quick_replies = []`.
- Промпт тем переписан под «ты», интерес вместо проверки, без рода, один вопрос, цитата по желанию. Список «никогда» — из брифа.
- Шаблоны `outreach.follow_up`, `outreach.day`, `outreach.anchor`, `outreach.farewell` — §2.4. Ключи `outreach.thread`, `outreach.yesterday`, `outreach.general` удаляются.
- Расписание, паузы, доставка, `farewell` и месячная сводка не меняются.

**Первый разговор (R257–R259, G04).**
- Все `first.*` на «ты» без рода (§2.4).
- Финиш, названный заранее:
  - `FIRST_SKILL_SCHEMA` и `FIRST_MOTIVATION_SCHEMA` получают поле `named_finish: string | null` — финиш, если человек сам его назвал (коротко, его словами: «B1»);
  - шаг skill кладёт его в `state.named_finish`, шаг motivation может его заменить;
  - `_finish_options` ставит `named_finish` первым, дополняет вариантами модели без дублей (сравнение через `verify.normalize`) и обрезает до `FINISH_OPTIONS_MAX`;
  - промпт motivation получает названный финиш, чтобы остальные варианты его дополняли.
- Сравнение — одна строка `first.comparison` (§2.4).
- `parse_hour`: число, перед которым стоит буква, не считается часом (`(?<![\w:.])`). «уровень B1» → `None` → переспрос. «в 9 вечера» → 21, «20:00» → 20, «8pm» → 20.

## 2.4 Тексты диалога на «ты» без рода (ru; en — обычное you)

Правки текста промпта брифа (остальное дословно):
- «естественно («ты же недавно говорил, что…»)» → «естественно («помнишь, недавно было…»)».
- «Не говори «ты рассказывал», если этого нет…» → «Не ссылайся на то, чего нет в переданных фактах или разговоре».
- Добавляется строка: «О человеке — без форм с родом: не «ты сделал», «ты справился», «рад, что заглянул», а «получилось», «ты с этим справляешься», «хорошо, что ты здесь». Если человек сам говорит о себе в роде — можно в его роде».
- «Не восклицай «как я за тебя рад!»» — остаётся как пример запрета.

Примеры (`bad` — дословно из брифа, род в нём не важен; `good` переписан):
1. good: «О, MVP — это уже не просто идея. Что получилось собрать?» (без изменений).
2. good: без изменений.
3. good: без изменений.
4. good: «Подожди. Месяц назад было {{quote:f_12}}, а недавно — {{quote:f_87}}. Что сейчас даёт ощущение, что всё стоит на месте?»
5. good: «Привет! Хорошо, что ты снова здесь. Как ты?»

Реплики человека в примерах — его слова, остаются как в брифе.

Шаблоны `texts.py`:
- `first.greeting`: «Привет! Я помогу тебе замечать, как ты растёшь, — твоими же словами. Что ты сейчас развиваешь?»
- `first.comparison`: «Смотри: в начале — {then}. Сейчас — {now}. Пройдено больше, чем кажется.»
- `outreach.follow_up`: «Недавно было: «{quote}». Как в итоге?» / “Not long ago: “{quote}”. How did it go?”
- `outreach.day`: «Как прошёл день? Что запомнилось?» / “How was your day? Anything stick with you?”
- `outreach.anchor`: «Привет! Давно не слышно. Как ты? Как сейчас с «{goal}»?» / “Hi! It's been a few days. How are you? How's “{goal}” going?”
- `outreach.farewell`: смысл прежний, на «ты», без упрёка и без «пропустил».
- Остальные `first.*` и `safety.*` переводятся с «вы» на «ты» с тем же смыслом и без рода. Ресурсы помощи (`SAFETY_RESOURCES`) не трогаются.
